# BRIDGIT audit: building toward comprehensive Android agentic control

**Advisory only.** I changed no files, ran no shell commands, touched no devices and published nothing.

## How I approached it

I took the Kotlin sources and the manifests as the record of what the app does, and treated the specs and `features.json` as proposals. I read these fully: `ApiServer.kt`, `Policy.kt`, `BridgeService.kt`, `Media.kt`, `AuditLog.kt`, `BridgeApp.kt`, both manifests, the debug receiver, the v3 spec, the similar-apps review, `spec-agent-inbox.md` and `spec-screenshot.md`. I read these in part: `MainActivity.kt` (by grep), `scenarios.md`, the relevant sections of the v2 spec, the README and `features.json`. I did not read `spec-per-agent-permissions.md`, the Grok review, or the website HTML and JS.

The only external fact I treat as verified is the Google Play Accessibility policy you supplied. Every other Android platform statement below is either quoted from the repo's own `[Verify]` notes or labelled as unverified platform knowledge.

The most important finding is the gap between what the app can actually do and what the website says it does.

## 1. What the app can do now, versus what's planned

### What the code actually does (v1.2.0, `minSdk 34` / `targetSdk 35`, `build.gradle.kts:17-24`)

There are exactly 11 routes, at `ApiServer.kt:52-66`:
- pairing
- reading and setting an agent's profile
- health
- a capabilities report
- a camera snapshot
- a microphone clip of 1–120 s
- a recent-photos list and a single photo
- the latest image (`image/last`)
- the audit log

There is no screen capture, no Accessibility service, no MediaProjection, no interactions or notices, no events, no MCP, no location, no text-to-speech and no controls. A search of `app/` for `interactions|screen/capture|AccessibilityService|MediaProjection|/mcp|events` found nothing, and the manifest (`AndroidManifest.xml:6-19`) declares no such service or permission.

**For control purposes, Bridgit today is a read-only sensor bridge.** It cannot act on the phone at all. "Screenshots" today means `image/last?type=screenshot`, which returns the newest file in a Screenshots folder (`Media.kt:214-240`). That only works after a person has taken a screenshot.

### Website overclaim (P0, not a feature gap)

`website/content/features.json` marks about 15 features `"status": "current"` that have no code in this tree:
- Screenshots on request (l.25)
- Questions and notices (l.98)
- Interactive cards, Live text, Audio playback/speech, Open a link (l.106–130)
- Events and callbacks (l.170)
- Location on request (l.187)
- Discoverable API, API change notices, MCP tools (l.317–333)
- Quick pause, Agent notes, Bug reports, App updates (l.366–414)

`feature-catalog.mjs:23` defines "Current build" as "implemented in the personal app build". That conflicts with v3 GATE-06 and §2, which says stages B–D must be labelled as planned. **Unless these features exist in a build outside this working tree, correct the catalog before publishing.**

## 3. Architecture for safe control

1. **Planes.** Keep v3 REQ-15's split between a control plane (pair, discover, propose, grant) and an execution plane. Activation and new grants happen only on the phone (REQ-16, l.90). A bearer key can never raise its own authority.

2. **Observe.** `POST /v2/observe` returns:
   - `obs_id`, `as_of`
   - foreground package and window
   - lock state
   - a `secure_content` flag
   - a node tree whose `ref` values are valid only for that `obs_id`
   - an optional screenshot

   Everything in an observation is marked as data, not instructions (REQ-26; similar-apps #2).

3. **Act with typed actions.** The vocabulary is a closed list: `tap{ref}`, `set_text{ref,text}`, `scroll{ref,dir}`, `global{back|home|recents}`, `launch{package}`, `wait_for{predicate,timeout}`.
   - No shell, coordinates only as a fallback, and limits on batch size.
   - Each action carries `obs_id`, an `idempotency_key` and an optional `expect` condition.
   - If the window has changed since `obs_id`, return `409 stale_observation`. Never act on refs that may now point at something else.

4. **Verify.** The result separates `dispatched` (Android accepted the gesture), `effect_observed` (the post-condition matched a fresh observation) and `confirmed` (the owner approved).
   - **A successful dispatch is never reported as success.** Ambiguous outcomes return `unverified` along with the new observation.

5. **Session leases.**
   - Request: `POST /v2/sessions {purpose, package_allowlist, scopes, max_duration}` → the phone shows a question with the agent's identity bound to its ID → the lease is granted.
   - One controller per device. A heartbeat is required, with a short TTL.
   - While a lease is active, a permanent "<Agent> is controlling" overlay and notification show a Stop button.
   - The lease pauses when the foreground app leaves the allowlist, on lock, and whenever the owner touches the screen. Whether user touches can be detected reliably is **unverified**; a Pause button is the fallback.
   - Removing an agent or rotating its key ends the lease (REQ-18).

6. **Consent tiers.**
   - Observe: covered by the lease.
   - Navigate and enter text: covered by the lease.
   - Commit (send, pay, delete, install, settings or permission changes, any outbound message): per-action confirmation on the phone, showing the action digest and the visible target text.
   - The agent proposes; the owner commits.

7. **Stale state.**
   - Every response carries `as_of` and a device `epoch` that increments on reboot, service restart or lease loss.
   - Desired and observed state are stored separately (REQ-19).
   - A reboot restores configuration only, never "running" status.
   - The capabilities report shows real readiness, for example `service_start_blocked`.

8. **Recovery.**
   - Steps are checkpointed.
   - On failure: return to an anchor (back or home, then relaunch the allowlisted app), observe again, and retry within a bounded limit.
   - After N failures, escalate to the owner as a question.
   - Cancelling releases all resources within the 2 s target.

9. **Events.** A per-agent cursor stream with gap markers. Types include `lease.*`, `action.dispatched/verified/failed`, `window.changed`, `user.intervened`, `device.locked`, `interaction.*`, `capability.changed` and `epoch.changed`. Signed callbacks are optional (EVT-05/06).

10. **Audit.** Records actor, lease, action type, target package, outcome class and request ID. It never stores raw text, tree content or media. Entries are scoped per agent and hash-chained so tampering is detectable.

## 5. Recommended next vertical slice: the consent and event spine

Agentic control is the goal, but the next slice should be **visibility hardening + per-agent scoping + interactions + events** (gaps 1, 2-lite, 3, 4, 5). The reasoning:

- Every later control capability needs an owner-consent channel and an asynchronous verify signal.
- MediaProjection consent itself has to start from an owner tap on a question (`spec-screenshot.md:46-50`).
- All of this is ordinary-app tier, needs no new risky permissions, and makes the approve-before-pay, send-steps, speak-aloud and approve-send scenarios possible right away.

### Acceptance cases for this slice

1. With POST_NOTIFICATIONS denied, or the capture channel disabled, camera and mic return `403 notifications_required`. Turning the channel off during a 60 s clip stops recording within 2 s and records `visibility_lost`.
2. With the phone locked, the mic follows the same documented lock policy as the camera. This is an explicit decision, not an accident.
3. A question from Codex, which has no webhook, is answered from the notification. Codex's `wait=55` returns `answered` within 1 s (from `spec-agent-inbox` test 1).
4. Two agents: each sees only its own interactions, events and audit entries. A third agent with no `interactions` grant gets `agent_not_allowed`.
5. The question header shows the identity bound to the authenticated agent ID. If the profile changes while the question is pending, the original identity stays on screen or the question requires fresh review.
6. Expiry, dismissal and agent cancellation each give the correct final status. Removing an agent withdraws its pending questions and invalidates its open waits.
7. The event cursor survives a service restart. A gap after retention cleanup returns an explicit gap marker. `epoch` increments on restart.
8. Retrying a POST with the same idempotency key returns the original result. The same key with a different body returns `409`.
9. Audit entries record the interaction ID, kind and outcome, never the title, text or answer values.
10. Text containing instructions in a question or answer has no effect on authority; an attempt to escalate scope fails.
11. Website catalog statuses match the build's `/v1/capabilities` (or `/v2/capabilities`).

### Following slice (`full` flavor, needs an owner decision reversing CAP-26)

Accessibility **observation only**, plus session leases, plus the overlay. Then a single typed action, `tap{ref}`, with a stale-observation `409`, `effect_observed` verification, Stop within 2 s, and pause when the foreground app leaves the allowlist.

Acceptance for that slice should also include:
- a `FLAG_SECURE` app returning `secure_content` rather than a workaround
- confirmation that the `play` flavor's merged manifest contains no Accessibility service
