Bridgit API

Bridgit: Comprehensive Device Manager for Android, version 1.6.0, API revision 8. What an AI agent can ask an Android phone to do, and the exact calls. Base URL http://<phone>:8734/v1 on the owner's Tailscale network; every call needs Authorization: Bearer <key> except where noted. A running phone also serves this live at GET /v1/guide and GET /v1/openapi.json.

Supported Agent Requests:

Available now

Take a photo

An agent can take a photo with the front or back camera. Android's green dot and a Bridgit notification show every time.

Options
  • Back or front camera
  • Zoom: 0.5× (ultra-wide) up to the phone's maximum (telephoto)
  • Flash on or off
  • Size: sized for AI (1568 px), thumbnail (512 px), large (2560 px) or original
  • Or an exact width or long edge, and JPEG quality
  • Resolution supported by the phone, camera pipeline and response limits
  • As JSON with the picture inside, or as plain JPEG bytes
  • Never saved to your gallery
For example

From your laptop: "Is the stove off?" Your agent takes a photo of the kitchen and tells you.

API
POST /v1/camera/snapshot Idempotency-Key details

Take a photo now.

POST /v1/camera/snapshot {"camera":"rear","zoom":2}

Questions and notices to you

Agents send you a notice, or a question with buttons, choices or a text reply, and receive your answer through the API or callback when the connection is available. They can also read it aloud.

Options
  • A notice (one-way) or a question
  • Buttons (up to 6), a text reply, a choice list, or a link
  • An image with the message
  • Normal or urgent; read aloud if you allow it
  • Expires after 1 minute to 7 days
  • The agent waits for your answer or gets a callback
For example

"Pay this invoice? $11.99" [Pay] [Not now]. Your reply is returned to the agent. Any payment requires an authorized payment tool and confirmation of the actual result.

API

Bridgit makes a setup prompt with the agent's own key, the address and the rules. Use it with a compatible agent whose HTTP or MCP tools can reach the phone’s Tailscale network.

Build an applet

An applet is a ready-made session between the owner and one agent, like City tour: the phone sends the agent data on a schedule or when the owner acts, and the agent answers out loud or with a question card. There are two ways to build one. Start with A; do B when the applet works and the owner wants a button for it.

A. Run it from your side (no app change)

Any paired agent can do this today with the calls below.

  1. Report your model once: POST /v1/me {"model","harness"}.
  2. Offer the applet with a question card: POST /v1/interactions with buttons, e.g. Start / Not now. Wait for the answer with GET /v1/interactions/{id}?wait=55.
  3. Keep one loop on GET /v1/events?since=<last id>&wait=55 (60 s timeout). If your harness only acts during a turn, run the wait as a background command so each event wakes you.
  4. Read what the applet needs on a timer you keep: GET /v1/location (with compass), POST /v1/camera/snapshot, GET /v1/image/last?type=photo, POST /v1/mic/record. Check GET /v1/capabilities first and ask the owner to switch on what is off.
  5. Talk back with POST /v1/speaker/say {"text"} (2-4 short spoken sentences; newer narration replaces what is queued) or a question card when you need a choice.
  6. Stop when the owner says so (a Stop button on your card) or after a time limit you announced. Only capture while the applet runs; every capture is shown and logged.

B. Add it to the Bridgit app (a coding agent with the repository)

Copy City tour. Each step names the City tour file to copy from; keep its rules.

  1. Write the spec first: a section next to 8.25 City tour in docs/bridgit-spec-v2.md with numbered rules like TOUR-01..07 (what it needs switched on, what is sent to whom, limits).
  2. Session engine: a manager like TourManager in tour/Tour.kt. One session at a time, one agent, sends <applet>.started (with a brief string telling the agent what to do), <applet>.tick, owner actions, and <applet>.ended through app.interactions.event(agentId, type, data). Create it in BridgeApp.
  3. Agent API: a Capability module like TourModule (register it in capability/Capability.kt), with an EndpointSpec for every call in api/Endpoints.kt and in Endpoints.all. Only the session's own agent may read it.
  4. Screen: a fragment like ui/tour/TourFragment.kt (setup: pick an agent and options, list what is missing; running: big buttons, what was said, End). Add it to res/navigation/nav_main.xml.
  5. Card: add it to res/layout/fragment_applets.xml and AppletsFragment, with a running chip.
  6. Tell agents: add an ApiChanges revision, a section in the live guide (api/SelfDescription.kt), and a "What can Bridgit do?" card in ui/more/WhatCanData.kt.
  7. Use the automatic APK version allocator; every APK build must reserve a fresh version name and code. Do not hardcode or lower the version counter, run ./gradlew testDebugUnitTest (ApiDocsTest checks every endpoint is documented), install, and try it on the phone with a real agent.

Rules every applet keeps: data goes only to the session's agent and only while it runs; the owner can always end it; nothing is kept afterwards except log lines.
